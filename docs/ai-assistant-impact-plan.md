# 大模型应用开发改造影响面计划

## 目标与范围

把现有商城助手从“已接真实模型的轻量 FAQ/商品问答”完善为可验证的 RAG 电商客服与业务助手，突出真实模型接入、Prompt 工程、知识检索、受控工具调用和业务权限。计划覆盖消费者客服、管理端知识管理、后端 AI 服务、MySQL/Redis 数据、测试与可观测性。

本计划只描述本地开发阶段的功能改造，不包含发布、部署、上线或生产环境配置。保持 Spring Boot 2.5.14，不为接入 AI 框架而升级全项目；先复用后端现有 OpenAI 兼容客户端，只有在明确收益后再评估依赖替换。订单、退款、支付等写操作不交给模型执行。

## 当前基线

| 能力 | 当前实现 | 对计划的影响 |
|---|---|---|

| 质量指标 | 请求数、检索非空率、工具成功率、平均耗时、token 与估算成本记录在进程内，通过后端指标接口读取；重启清零，后台无指标页面。 | 需要区分“检索非空”与“检索相关”，为评测及运营提供可追溯的聚合数据。 |
| 测试基线 | 已有 WebSocket 隐私和订单工具归属测试；尚无 Prompt/RAG 相关度、引用正确性、流式协议、失败降级和工具白名单的系统测试集。 | 先为现有安全边界补齐可复现回归，再逐阶段增加 RAG 和端到端覆盖。 |

## 按影响范围分期

### P0：安全边界与可验证基线

**影响范围：**`service/Neuedu-admin` AI WebSocket、模型服务、鉴权与工具测试；`user/` 客服协议兼容。

- 保持模型密钥只在后端运行配置中；日志仅记录错误类型、延迟、token 与计数，不记录密钥、完整用户问题、订单号或完整模型请求体。
- 将模型可调用工具作为显式白名单；后端再次校验工具名称、参数类型、长度、状态枚举和登录身份，永远不使用模型提交的用户 ID、订单号或角色。
- 检索到的 FAQ、商品资料和用户文本都按不可信内容处理。Prompt 明确说明资料不是指令；工具执行前不因 Prompt 内容改变权限。
- 保留现有订单只读和脱敏行为；任何未来的退款、取消、下单动作都必须由应用端请求并由用户显式确认，不允许模型直接写订单。
- 新增模型客户端 mock 和表驱动测试：匿名/越权订单、伪造身份参数、未知工具、非法参数、上游超时/错误、空模型响应、敏感字段不出日志。

**验收：**无需真实模型密钥即可稳定运行安全测试；模型或检索故障只返回安全降级和转人工提示；现有用户订单隔离测试继续通过。

### P1：Prompt 工程与离线评测

**影响范围：**后端 Prompt 组装、配置/资源文件、AI 服务测试；客服回答的格式约定。

- 把单段 `systemPrompt` 拆为有版本号的 Prompt 模板和上下文组装器，分清系统规则、当前访客身份、商品/订单实时事实、RAG 引用和最近对话历史。
- 按问题意图选择必要上下文：商品推荐/价格库存、配送售后政策、订单状态分别提供对应约束；避免把所有 FAQ/商品描述长期堆进系统提示。
- 对引用资料使用明确分隔和来源标识，要求回答只引用相关资料；无来源或来源冲突时说明不确定并转人工。模型输出中的来源只能来自后端检索结果，不能接受模型自造引用。
- 建立固定评测集：常见售后问题、商品问法改写、无答案问题、提示注入、越权订单问题、来源冲突和工具调用场景；记录期望答案要点、允许来源和禁止行为。

**验收：**模板可单独修改并有版本记录；相同 fixture 可重复执行；安全拒答、来源引用和工具边界有明确断言，不以“调用成功”代替答案质量。

### P2：知识库数据模型与管理入口

**影响范围：**MySQL 知识表/迁移、`AIKnowledgeController` 与服务层、`admin/src/views` 管理页面、动态菜单/权限、前端 API 封装。

- 在现有 FAQ 之外增加可管理的知识文档与片段概念，至少包含来源类型、标题、正文、商品/类目范围、草稿/启用状态、版本、更新时间和内容摘要；保留 FAQ 兼容读取。
- 支持管理员录入、编辑、预览、启停、按商品/类目筛选和查看更新状态。后端负责校验内容长度、作用范围和发布状态，前端权限按钮不能替代接口权限。
- 数据迁移只做向前兼容的新增表/索引和可重复初始化；不覆盖现有 FAQ，不清空商品或业务数据。数据库变更先提供脚本与回滚说明，再在本地目标库验证。
- 通过后台动态菜单及既有权限注解授权知识读写；消费者端不暴露知识编辑或指标管理接口。

**验收：**管理员可在界面维护一条知识并检索到该条来源；无权限账号读写均被拒绝；升级脚本重复执行不会覆盖已有答案或业务数据。

### P3：语义与混合 RAG

**影响范围：**后端知识导入/切片、Embedding 接口、检索适配器、向量存储配置、引用协议、相关度评测；本地开发需要可启动的向量检索依赖。

- 将文档拆成有稳定 ID 的片段，保留标题、来源、商品/类目范围、版本和生效状态等元数据；文档变更时只重建受影响片段。
- 增加可替换的 Embedding 与向量存储接口。建议本地开发使用独立、可本机运行的向量存储适配器；模型及存储地址通过后端配置提供。不要把向量字段塞进商品业务表，也不要把动态库存/价格当静态知识向量化后视为实时事实。
- 先用关键词召回与向量召回做混合候选，再按权限/商品范围过滤；加入最小相关度阈值。低分、无资料或资料冲突时拒答/转人工；重排作为测得收益后的第二步。
- 商品实时价格和库存以数据库工具查询为准；FAQ、配送和售后政策走知识检索。前端来源结构增加可识别的来源类型与稳定来源 ID，展示可核验标题/片段。

**验收：**同义改写问题能召回正确片段；无关问题不会因“有候选”而被算作有效命中；评测集记录 Recall@K、MRR/相关度阈值、引用正确率和无答案拒答率；向量服务不可用时安全退回关键词检索或人工客服。

### P4：业务工具边界与结果结构化

**影响范围：**工具定义/执行层、商品和订单读取服务、权限/隐私测试、客服卡片展示。

- 保留现有商品搜索和“我的订单”工具，内部将职责收敛为清晰、只读的查询工具，例如商品搜索、单商品价格库存、当前用户订单状态；不允许通用 SQL、任意 URL、任意用户 ID 或自由执行代码。
- 工具响应采用结构化结果并限制条数/字段：商品返回 ID、名称、价格、库存和详情入口；订单只返回当前用户少量记录、状态和脱敏标识。
- 服务端对所有工具执行独立鉴权、参数校验和结果裁剪；模型只能提出工具请求，不能自行声称工具成功。工具失败要返回明确的失败状态供模型安全解释。
- 与模型协议兼容地处理工具调用轮数上限、重复调用和无效 JSON；超过上限时结束本轮并给出转人工入口。

**验收：**工具输出不泄露其他用户数据；实时价格/库存来自当前商品记录；未知工具和非法参数不触发业务查询；模型请求写操作时被拒绝。

### P5：会话体验、人工交接与质量观测

**影响范围：**WebSocket 协议、`user/src/views/chat`、人工客服消息入口、Redis 会话状态、指标接口与管理页面。

- 稳定 stream/sources/handoff/error/end 事件语义；前端展示连接、断线、重连、超时、重试和部分回答状态，重试不重复提交已完成的业务动作。
- 让 RAG 来源卡片可展开查看标题、来源类型和相关片段；无法回答时提供明确的人工客服入口并带上用户主动选择转交的上下文。
- 若需要跨连接恢复历史，先定最短必要保留期限、用户清除入口和敏感字段策略；优先用带 TTL 的 Redis 会话，而不是无期限保存完整聊天文本。未定义保留策略前不持久化原始对话。
- 将质量统计从内存累计扩展为可查询的聚合数据：有效检索率/低分率、引用正确率、工具成功率、转人工率、响应 P50/P95、token 与估算成本。避免记录原始问题及个人数据。
- 增加管理端客服质量视图，沿用现有路由、动态菜单和权限，不因指标展示而开放客服内容或密钥。

**验收：**断线与上游失败可恢复或安全结束；用户能看懂来源与转人工状态；聚合指标重启后仍可按时间查询且不包含原始聊天内容。

## 执行顺序与依赖

1. 先做 P0 与 P1：锁定权限/失败边界并建立离线回归集，为后续 RAG 和工具改造提供红线。
2. 再做 P2：先有文档生命周期和管理入口，再接向量索引，避免向量库中出现不可维护的知识副本。
3. 做 P3：先完成关键词与向量混合召回、低置信度处理和引用验证；此阶段只支持本地可运行的向量依赖，不涉及生产部署。
4. 做 P4：基于检索之外仍需实时读取的数据补齐受限工具；权限边界和只读约束先于前端卡片体验。
5. 最后做 P5：在会话保留策略明确后增强断线体验和指标持久化/管理页面。

每个阶段保持 API 兼容或同步更新消费者端调用；一阶段一验证，中文提交。真实模型联调只有在本地配置密钥后执行；未接入凭据或向量服务时，报告对应路径未验证，不阻塞其余离线测试。

## 本轮边界

本文件是实施计划，不代表计划中的 AI、数据库、管理端或客服改造已经完成。本轮只整理影响范围和验收条件；不升级 Spring Boot、不改数据库、不新增向量服务、不生成发布产物，也不改生产部署配置。
